# 产品与建设方案

更新：2026-10-21。技术初选见 [技术方案](technical-plan.md)，决定状态见 [决策记录](decisions.md)。

## 已确认

- 主要使用地：中国国内。
- 当前只有本人编辑，预留多用户管理与权限接口。
- 希望生成徒步路线，并关联图文日记；不希望依赖持续开启轨迹记录 APP。
- 核心场景为出发前规划、回来后记录；不需要离线打开地图（2026-10-20 确认）。
- 思源《中国国内游玩路线图谱》是重要资料源。
- 复用本机 MySQL。
- 长期维护，逐步支持 AI 咨询、出行信息整理。
- 前后端统一放在 `/opt/projects/travel-journal`。
- 技术方向于 2026-10-20 确认：Vue 3 + Vite 前端、Node.js + TypeScript 后端、本机 MySQL；先建设适配手机的网站，预留 Capacitor 安卓打包。
- 用户管理、资料维护、思源同步及 AI 配置等由独立 Web 管理端承担，使用端仅保留个人设置。
- 原型由用户在 OpenDesign 更新和预览，助手默认只读评审、提供提示词。使用端当前版本为 v4；当前不等同于正式应用上线。
- 后续用本仓库文档持续记录设计及选择，修改依据与验证边界可追溯。

## 使用端与管理端

| 页面 | 职责 |
| --- | --- |
| 地图 | 已到访／想去、年份、行政区层级、城市记忆与关联计划 |
| 旅程 | 路线资料、跨城市目的地、分日地点、交通、可选住宿、计划与实际记录 |
| 回忆 | 独立或关联行程／某天的图文日记、照片说明、草稿、阅读及分享 |
| 我的 | 个人资料、统计、心愿、个人设置 |
| 独立管理端 | 用户与角色、资料管理、思源导入审核、服务配置、任务与必要审计 |

两套前端独立构建、共用模块化单体后端是建议架构，不要求拆为两套业务服务。

## 核心流程

行前：浏览资料／自行创建 → 出发地与多目的地 → 分日地区、地点、接驳与可选住宿 → 调整路线 → 保存计划。

回程：标记完成 → 主动复制计划或新增实际记录 → 独立修订 → 确认到访 → 写日记与关联照片 → 设置分享并预览。

标记完成与复制计划均不自动新增到访、日记或照片。已有实际内容复制前明确选择追加或替换；计划与实际分别保存。

## 路线生成

持续定位将经纬度、时间、可选海拔连续记录，形成 GPS 实录。没有定位数据时无法恢复唯一真实路径。

首版推荐：选择路线模板或填写起点、途经点、终点 → 地名匹配并确认 → 在已知路网上逐段规划 → 手动调整 → 保存路线草稿 → 添加图文日记。

可以读取原始照片 EXIF 的位置和时间作为途经点；照片无定位或元数据被移除时支持手工选点。拍照时刻不能代表完整运动时间。路网不足的路段保留为待确认或明确标识的示意连线，不能伪装成已确认可通行步道。

每段路线记录来源（GPS 实录、导入参考、路网规划、手工补绘）、源坐标系、确认状态和可用的原始数据。规划路线里程为估计值，不生成虚构的实际速度、耗时或爬升。

参考 GPX 可导入，但别人的轨迹不能自动变成自己的实录。AI 负责提取地点、检索和解释；路线几何由路线数据、路由服务及人工编辑产生。

## 业务对象

- 用户与权限：从第一版就为行程、日记、附件设置 owner_id；仅启用管理员账号，关闭公开注册。用户管理接口按实际需要逐步实现。
- 目的地：地点、别名、地区、坐标及坐标来源。
- 路线模板：可反复采用的路线知识、途经点、季节与难度。
- 行程：出发地、多目的地、日期、参与者、状态、私人准备事项。
- 每日安排：地区、地点顺序、交通、选填时间、备注与可选住宿；地点可跨城市、跨日移动。
- 路线版本与路段：支持计划、补绘、实录并存。
- 日记与媒体：文字、照片、时间、地点以及分享范围。
- 资料来源：思源原文、官方信息、社区参考、最后核验时间。
- 分享记录：私密、持链接可见、公开；服务端判断访问范围，后续支持撤销链接。

一条路线可以对应多次出行；一趟旅行可以包括自驾接驳和多段徒步。资料库没有去过的路线不能标成个人足迹。

## 已确定技术方向

客户端采用 Vue 3 + Vite + TypeScript，优先建设适配手机的网站，预留后续通过 Capacitor 打包安卓应用的能力。后端提供独立 HTTP API，MySQL 使用现有实例、新建专属数据库和低权限账号。网页与安卓客户端共享业务 API。

后端采用 Node.js + TypeScript。当前业务以 MySQL 查询、思源同步、地图服务和外部 AI 接口调用为主，Node.js 的异步 I/O 模型适合这些任务，也便于前后端复用类型和校验规则。TypeScript 的类型不能替代请求参数及外部响应的运行时校验。具体后端框架与数据库访问库在实现阶段选定。

首版采用模块化单体，分为账号与权限、行程日记、路线、思源接入及 AI 模块。批量导入和图片处理限制并发、可恢复；CPU 密集的 JavaScript 计算在必要时使用工作线程或独立进程，不阻塞接口主线程。路线规划优先调用已有路由服务，不以自研全国路网引擎作为首版目标。暂不拆微服务。

地图优先验证高德在实际目标路线的地点搜索与路线覆盖；徒步规划通过可替换的路由适配层接入。不能假设城市步行导航完整覆盖山地小路。GPX/照片 GPS 常为 WGS84，高德使用 GCJ-02；保留原始坐标和坐标系标识，显示与导出执行明确转换，不混存或重复转换。

媒体使用可替换的存储接口，优先考虑对象存储；资源现状见 [有日期的数据源调查](data-sources.md)。地图按需加载，照片缩略图与原图分开，避免首屏加载大图和全部轨迹点。

AI 接入外部模型服务，保留供应商适配接口。第一阶段先做地区、月份、天数等结构化筛选和关键词检索；检索质量需要时，再复用已有 Qdrant 加入语义检索，不在当前服务器部署大模型。

## 思源与 AI

思源维护研究资料，网站维护结构化路线与实际出行；首版单向读取思源并保留来源，避免双向编辑冲突。导入先生成可审阅草稿，别名和跨索引重复路线合并，缺少数据明确留空。

问答流程：用户条件 → 权限内检索 → 挑选路线与依据 → 必要时查询当前信息 → 生成带出处和日期的回答／行程草稿。

知识检索先过滤 owner_id 与可见性。个人资料不能因公开问答而泄漏。门票、开放状态、天气、交通等动态信息与一般景观介绍分别存储；没有实时查询结果时显示资料日期与未核验状态。
