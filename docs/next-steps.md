# 后续建设顺序

整理日期：2026-10-31。用户已明确：当前是测试阶段，优先完善后台管理，运行保障放到后续低优先级。当前顺序为后台整理 → 思源资料库 → AI → 运行保障；思源与 AI 的具体分批内容仍是建议。

## 当前起点

行程工作区、照片回忆、分层足迹地图、路线／GPX 工具、可撤销行程图文快照与独立管理工作台已有实现。管理端目前以全局只读台账、账号操作、分享撤销与配置摘要为主；思源和 AI 尚未接入。

仍待补齐：数据库＋照片＋配置的整体恢复演练、自动备份与运行恢复；真实手机照片／键盘／触摸操作验收；管理端可操作的资料整理流程。绿色轨迹贴纸有本机样张，尚无正式产品导出入口，不能把既有行程分享链接说成已支持精确轨迹分享。

旧 [首版实施清单](implementation-plan.md) 保留 M0–M5 里程碑背景；当前下一节点顺序以本文为准，已交付内容及验证以各专题为准。

## N1：管理端内容整理（当前优先）

目标：用现有台账处理真实的资料维护需求，不重复建设使用端行程编辑器。

状态：本轮已实现状态／待整理筛选、照片受控预览与单张日期／备注／地点整理、本人资料编辑入口，见 [后台资料整理](admin-curation.md)。批量整理仍是后续批次。

分批范围：

1. 状态筛选与待整理清单：旅程状态、照片精确位置／日期缺失、到访城市待归属；从概览进入即带筛选条件。
2. 照片受控预览、关联旅程／日记与明确编辑入口；当前本人账号可直接衔接使用端编辑。未来多账号内容不能简单跳转到无权访问的本人编辑页，也不把后台预览权限直接扩成公共原图 URL。
3. 必要的批量整理：先支持选定照片的日期／地点修订预览、确认和版本冲突保护。仅给待整理记录补信息，不静默覆盖已有精确位置，不自动新增到访。
4. 存储占用、已有任务失败与操作结果保留真实摘要；备份、运行恢复等另归后置阶段，不在当前批次扩展。

完成标准：能在后台找到一组待整理资料，核对原图及来源，完成支持的修订或准确进入使用端编辑，刷新后结果一致；冲突与失败不会显示成功。每个可视节点依约两轮实图自审。

首批不增加复杂组织／角色体系、跨用户批量删除或在线环境密钥编辑器；目前本人使用的需求优先。

## N2：思源资料库（M5.1）

目标：让已有路线研究资料先成为可查、可引用、可复用的资料，不以 AI 为接入前提。

- 重新只读核对配置指定的笔记本／根文档范围；历史调查的文档数不是当前数量或路线条数。
- 首批建议挑 5–10 篇不同结构样本，验证详细卡、简表、索引、重复引用和附件；通过后再扩大范围。
- 后端单向读取，保存原文快照、来源文档／块 ID、内容指纹及同步时间；不回写思源。
- 地区、路线节点、天数、季节、标签、来源链接等提取成待审核草稿；原文、提取结果与人工修订分别保留。
- 管理端提供同步结果、审核、更新差异、忽略／重试和关键词检索。新增或变化不覆盖人工修订、既有行程或旅行回忆。
- 审核后的资料可作为行前参考；采用为旅程时生成新的待确认安排，不直接产生已到访足迹。

完成标准：能搜索一份资料、查看原文依据、审核提取内容；思源修改后出现可核对的新版本，旧行程与人工修订不被覆盖。供应商／笔记网络故障不影响正常行程和照片功能。

## N3：AI 咨询与整理（M5.2）

目标：基于自己的资料回答真实出行问题，并减少整理地点的工作量。

- 先实现带引用的资料问答，例如“湖北周边两天有什么徒步路线”“某线路哪些信息还需确认”。引用能回到来源，缺资料时明确说明。
- 再实现自然语言提取地点、整理候选路线与多日计划草稿；用户核对后才写入旅程，优先复用已有“待安排／分天”工作区。
- 先用 MySQL 结构化筛选与关键词检索评估实际问题，再按检索质量决定是否增加语义索引；不预先引入本地大模型或额外向量库。
- 模型配置、凭据、调用限额、失败与费用统计归后台；请求只使用权限内、必要的资料。把私密笔记发送外部模型前需明确模型供应商及发送范围。
- 地图／路由服务和人工核对负责几何，AI 不补造实录轨迹、速度、耗时、爬升；动态票价、开放状态、交通等没有当期查询依据时保留资料日期与待核验状态。

完成标准：用一组约定的真实问题验证检索、引用和资料缺失行为，能预览并主动采用规划草稿；AI 故障不阻塞已有功能。此阶段再确定具体模型与预算，不在本文预设供应商。

## N4：运行保障（后置，承接 M4.2）

当前不实施。后续准备长期使用时，再完善可恢复性、域名 TLS 和运行恢复，不作为本轮后台开发前置。

- 核对管理域名 HTTPS、反代与 Cookie 行为，保留精确 Host／Origin；主站与后台分别验证登录、退出与会话到期。
- 将数据库、私有媒体和必要配置纳入同一次可核对备份，明确保留周期、空间与失败记录；敏感配置不进入 GitHub。
- 在隔离目标中恢复，核对照片可读、地点与行程关联、路线文件及分享撤销状态；不覆盖正式库。
- 补充 screen 启停、故障恢复和服务器重启后的操作说明，按实际需求再落实自动启动／恢复；不切换 systemd。

完成标准：完成一次隔离整体恢复与数据核对，备份任务有最近成功／失败记录，现有入口在桌面及手机访问路径下可用。备份文件存在不等于完成恢复验收。

## 按需要插入的小迭代

| 方向 | 实际价值 | 当前边界 |
| --- | --- | --- |
| 绿色轨迹贴纸／路线照片卡 | 将现有路线导出为可叠照片的 PNG，复用已有样张经验 | 来源与署名可辨认；公开几何分享另行定义范围 |
| 手机使用回访 | 用本人小米浏览器完成一次新建、地点搜索、照片上传与补位置 | 尺寸模拟不能代替真实相册、输入法、手势和网络 |
| 照片规模与性能 | 根据真实数量补服务端分页、筛选与上传恢复 | 不为了预想的大库提前重构全部媒体存储 |
| 路线与地图补强 | 根据实际出行补地区数据、POI 与路径核对 | 没有路网证据的连接继续明确为示意或待核对 |

继续保持 Vue／Node.js／TypeScript／MySQL 与独立管理端，网页优先；不将安卓打包、离线地图、多租户、复杂高程或全国路由作为近期前置。

## 每个节点的交付约定

先核查当前状态，写明本批可验收操作；涉及数据迁移先备份，在隔离环境验证；界面变更完成两轮实图自审后再更新预览。记录测试与未覆盖限制，按已授权流程提交推送代码和文档，私有资料、密钥、备份和截图不推送。
