## 2. 地图试点建议

从已有资料选东湖城市／湖畔步行、黄山正规步道、徽杭古道、长坪沟至木骡子，以及一个跨城混合日程。它们是技术样本，不表示本文件确认当天开放或建议直接出行。

每条样本先由用户或可靠资料确定目标入口、途经点、预期路径和当前适用范围，再比较供应商返回。不能只用“接口返回成功”判定路线正确。

如果高德无法覆盖关键徒步段，再针对同样本比较腾讯及 OSM 徒步服务；不要求一次接入所有供应商。不可用的段允许以导入或补绘完成，不能把直线作为自动算路成功。

整体覆盖率和可接受误差在样本确定后约定，当前不编造固定通过比例或性能结论。保存与导出授权不明确时，不把依赖该能力的产品承诺定案。

## 3. 建议执行顺序

1. 确定样本、地图账号与适用权限，先核对数据使用范围。
2. 验证 POI 与路段，对错误结果留样；验证坐标和文件互通。
3. 用真实思源卡和少量手机照片验证提取及媒体链路。
4. 根据证据锁定供应商及框架、数据结构，进入 API 和两套前端实现。
5. 基础检索有效后比较外部 AI 模型，必要时引入 Qdrant。
6. 网站稳定后验证安卓；上线前验证服务权限、资源和恢复。

## 6. 高德 WebService 首次连通性验证

日期：2026-10-21。触发：用户完成 `.env` 填写。执行环境：本机 Python HTTPS 请求，读取配置，不输出密钥、不修改 OpenDesign 文件，不保存完整供应商响应或路线点串。

### 配置检查

- `AMAP_JS_KEY`、`AMAP_JS_SECURITY_CODE`、`AMAP_WEB_SERVICE_KEY` 均有值。
- `.env` 权限 `600`，Git 忽略检查通过。
- JS Key 和安全密钥本轮只检查存在性；不能据此判断 JS 鉴权或浏览器加载成功。

### 实际调用

共 5 次：2 次 `/v3/place/text`，3 次 `/v5/direction/walking`（含 1 次针对端点差异的复核）。均返回 `status=1`、`infocode=10000`。

| 调用 | 结果 | 单次观测耗时 |
| --- | --- | --- |
| 搜索“东湖听涛景区”，限定武汉 | 返回景区及停车点等候选 | 364ms |
| 搜索“东湖梨园”，限定武汉 | 返回梨园景区、地铁站及广场等候选 | 375ms |
| 首候选坐标 + 对应 POI ID 规划步行 | 1 条路径，服务估计 102m／82s，2 步，含几何 | 122ms |
| 相同坐标、不带 POI ID 规划步行 | 1 条路径，服务估计 1040m／832s，10 步，含几何 | 152ms |
| 带 POI ID 的端点复核 | 复现 102m／82s，几何首尾与所传点显著不同 | 155ms |

这些耗时是少量本机观测，不是性能基准或 SLA；距离、时间是供应商规划估计，不是实际徒步测量。

### 发现：POI 与坐标模式的端点差异

两个候选坐标之间的近似直线距离约 801m。仅传坐标时，路线几何首尾距请求点约 27m／21m；带 POI ID 时约 1026m／298m。偏移为对返回几何首尾的球面近似诊断值，未经现场核对。

两种请求的 `route.origin`／`route.destination` 均仍显示输入点。因此不能只读取这两个回显字段判断实际路线端点是否符合用户选择；要核对几何首尾。

目前只确认 POI ID 改变了本样本的结果；可能涉及服务选择景区出入口或路网点，具体机制尚未证实。不能把 102m 判定为用户确认起终点间的完整路线，也不能把 1040m 当作已经人工确认的推荐线路。

### 对实现与选型的影响

1. WebService Key 在这些接口上可用，搜索、算路和返回几何的基础链路成立。
2. 搜索结果需展示对象类型并选择景区／入口／车站，不能直接采用首候选。
3. 用户确认具体位置后，对算路几何首尾做偏移检查；超出约定容差时提示确认入口或重新选点，不能静默接受。
4. POI ID 不应对所有类型无条件附加；其效果需按服务文档和实际样本评估。
5. 下一步验证浏览器 JS 地图、详细入口与典型山路；长期保存、修改和 GPX 导出授权仍未确认。高德仍为首个验证候选，未最终定案。

官方接口：[POI 搜索](https://lbs.amap.com/api/webservice/guide/api-advanced/search)、[路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)。

## 7. 浏览器地图与山路样本初测

日期：2026-10-21。用户要求继续验证后执行；仅使用临时脚本和回环地址测试页面，不修改 OpenDesign 原型或正式应用源码。测试结束后关闭临时浏览器及 HTTP 服务。

### 7.1 浏览器地图与服务端安全代理

环境：本机 Node.js v24.13.0、Playwright 1.60.0、独立 Headless Chrome；页面由 `127.0.0.1` 临时端口提供，加载高德 JS API 2.0。按官方 `serviceHost` 方式设置同源 `/_AMapService` 代理，安全密钥仅在服务端附加；浏览器只接收 JS Key，不接收安全密钥或 WebService Key。

共运行两次：第一次检查初始化、搜索及尺寸适配；第二次为确认实际绘制而检查图片加载并查看临时截图。每次 `/v3/log/init` 与 JS 插件的 `/v3/place/text` 均经代理成功，返回 `status=1`、`infocode=10000`。SDK 与底图资源另有网络请求，不能把这 4 次代理调用当作全部网络量或账号计费用量。

| 检查项 | 实测结果 | 边界 |
| --- | --- | --- |
| 地图初始化 | SDK 加载，触发 `complete`，中心为指定东湖坐标 | 只覆盖本机回环地址，不证明生产域名可用 |
| 底图实际显示 | 第二轮观察到 20 张 256px 瓦片已加载，查看截图确认地图、地名与署名可见 | 当前环境采用图片瓦片及 SVG；未验 WebGL／3D |
| 业务覆盖物 | 成功添加 1 条两点示意折线 | 仅验证绘制，折线不是算路或实际轨迹 |
| JS 地点搜索 | `AMap.PlaceSearch` 返回 `complete / OK`，获得 1 个候选 | 不证明候选位置已人工确认 |
| 手机宽度 | 从 1100×760 调整到 375×812，地图尺寸跟随，缩放到 15，无页面横向溢出 | 不是安卓 WebView 或手机真机验证 |
| 错误观测 | 两次均未捕获页面脚本错误、控制台 error 或失败请求 | 限所测时段与操作 |

临时截图只用于本机检查，不作为公开海报或长期存档素材。正式接入仍需验证域名限制、HTTPS、代理限流及来源控制；当前临时代理不作为可直接上线的实现。

官方依据：[JS API 安全密钥使用](https://lbs.amap.com/api/javascript-api-v2/guide/abc/jscode)。

### 7.3 三个坐标模式步行样本

调用 `/v5/direction/walking`，只传候选 GCJ-02 坐标，不附加 POI ID。首次每条请求 `show_fields=cost,polyline`；为检查索道等类型，再各复核一次，增加 `navi`，共 6 次，均返回 `status=1 / infocode=10000`，复核距离一致。

| 样本（只测所列路段） | 返回距离 | 服务估计时间 | 首／尾距请求点 | 首次耗时 |
| --- | --- | --- | --- | --- |
| 徽杭古道浙江入口售票处 → 蓝天凹 | 3153m | 2522s，约 42 分钟 | 约 36m／0m | 122ms |
| 黄山云谷寺 → 白鹅岭 | 3085m | 2468s，约 41 分钟 | 约 22m／18m | 91ms |
| 长坪沟喇嘛寺保护站 → 木骡子 | 9976m | 7981s，约 133 分钟 | 约 34m／837m | 93ms |

端点偏移按返回几何首尾与所传坐标的球面近似距离计算，不是测绘精度指标。三条均有非空点串，首次分别有 152／163／161 个点（包含分步接缝点，未去重）；完整点串仅在调用进程内分析，未保存到仓库。

本轮发现：

1. 长坪沟样本即使不传 POI ID，终点仍偏移约 837m。这条候选路线不能作为已到达木骡子的完整规划，也不能把缺失部分静默接成直线。
2. `walk_type` 在请求 `navi` 后位于 `steps[].navi.walk_type`。复核三条均返回 `0`，道路名称均为空。未标索道不等于已经确认实际没有索道、封闭路或不适合徒步的段；仍需与可靠线路资料或有权使用的参考轨迹比较。
3. 三条耗时均近似等于距离除以 1.25m/s，未获得爬升、地形或体能模型的证据，不能直接用作山地徒步预计耗时。应保留“供应商步行估计”标签，允许单独填写参考时长及来源。
4. 返回结果证明这些节点间存在服务规划几何，尚未证明覆盖完整古道、黄山指定登山步道或长坪沟目标线路。当前不出具线路正确率或出行建议。

官方字段：[路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)。

### 7.4 对方案的影响及下一步

- 高德 JS 地图 + 服务端搜索／算路的基础接入可行，可继续作为第一候选；供应商仍未最终锁定。
- 路线结果需有“待确认／端点异常／已确认”等状态，保存所选点与几何实际端点的诊断结果；容差应按场景确定，当前未硬编码统一阈值。
- 地图选点与候选选择允许用户调整具体入口。自动结果异常时保留未覆盖部分，支持合法来源 GPX 或明确标注的补绘。
- 下一步优先确定这三条路线的可信参考和验收节点，核对高德结果；有具体缺口再针对同段比较其他服务，避免仅扩大调用量。
- 长期保存、编辑分享和 GPX 导出权限仍需确认。正式域名、账号配额、限流、生产资源与安卓尚未验证。

### 11.3 默认 profile 的实际边界

1. `allow_steps=true`、`add_beeline=false`，适合本次台阶路段的技术探索；不要默认用直线补齐未知部分。
2. `consider_elevation=false` 表示未启用该开关的爬升偏好／代价项，不等于输出完全没有高程，也不等于时间估计已获验证。
3. 虽然有 `SAC_scale_limit=3`，所读脚本对超限使用 `SAC_access_penalty=999` 等代价逻辑；不能仅凭参数名称承诺高难度段被硬禁止。缺少 `sac_scale` 也不能被解释为低难度。
4. 所读脚本设置 `badoneway=0`、`onewaypenalty=0`，尚未证明它正确覆盖所有行人单向和复杂通行约束。本次线路不具备这类规则的验收覆盖；正式采用前需要选择／调整 profile，并用实际单向、禁行及缺失属性样本验证。
5. 公共服务自报 beta 引擎，profile 与源数据版本也可能变化；上线应锁定所用版本及配置，并决定托管接入安排或区域自建，不能直接把本次公共接口当作长期无限可用的业务后端。
