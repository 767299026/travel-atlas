# 旅程交互反思与案例研究

日期：2026-10-28。状态：问题核查与讨论草案。用户最初要求先研究；随后要求出首版提示词观察原型构造，已记录于 [旅程原型提示词](journey-prototype-prompt.md)。用户随后更新了旅程原型，已完成下文两轮只读评审；应用改版尚未实施，本文建议尚未整体定稿。

## 用户明确反馈

- 去掉旅程列表底部常驻“新建旅程”，保留右上加号并加深颜色。
- 新建及逐地点录入过于繁琐，天数越多负担越大。
- 新建后缺少删除旅程的方式。
- 经纬度输入不符合日常规划习惯；地图选点应首先支持搜索定位，不能要求人在大范围地图上准确点击。
- 本轮重点是操作逻辑，不急于实施或生成页面原型提示词。

## 源码核查与反思

本轮只读核查 JourneyList、JourneyCreate、JourneyEditor、RouteMap 及后端路由，未操作本人数据或进行手机可用性测试。

| 当前情况 | 使用者实际承担的负担 |
| --- | --- |
| 列表顶部加号、底部新建、空状态新建并存 | 常驻操作重复，占用内容空间 |
| 创建页展示名称、出发地、目的地、日期、天数，默认三天 | 即便部分选填，仍要求人在开始时思考尚未确定的信息 |
| 添加地点展示名称、地区、用途、时间、交通、备注 | 地点选择被做成逐条填写的表单；名称与真实地图位置又分开处理 |
| 弹层确认后还要保存整份行程 | 两次确认，容易混淆已加入草稿与已经存到服务器 |
| 排序需逐地点菜单操作，跨天移动又有弹层 | 少数基本整理动作随地点数量成倍重复 |
| 删除一天前要先移除或移走其地点 | 实现约束直接转成用户的清理劳动 |
| 地图／GPX 独立工具页，支持地图点选和折叠的坐标输入 | 普通地点选择与专业路径编辑混在一起，主流程缺少地点搜索 |
| 旅程只提供状态调整，没有完整删除入口／接口 | 创建的可逆性缺失；归档无法替代删除误建旅程 |
| 计划、实际、到访确认、照片／日记分布在不同操作里 | 用户需要反复理解内部对象，回来补记可能又做一遍规划劳动 |

反思：此前偏重模块和数据能力完整，缺少按真实任务贯穿的易用性验收。把字段改成选填、把坐标折叠，不能解决先后顺序、重复录入和操作中断。内部仍可保留日期、地点、分段、计划／实际等结构，但不应要求使用者逐项维护。

## 已核查的现实案例

资料核查日期均为 2026-10-28，来自官方产品介绍／帮助文档；没有登录其产品完成真机全流程试用，也未核实付费范围。

1. 高德地图：地点名称／地址搜索、搜索建议与结果列表；结果与地图联动，从地点可直接进入路线规划；地图选点是并列补充入口。参考[地点搜索](https://www.amap.com/ssr/doc/search)、[路线规划](https://www.amap.com/ssr/doc/route-plan)。可借鉴“搜索真实地点，再加入安排”，不照搬其导航和大量商家信息。
2. Wanderlog：行程与地图按天或分类组织；地点可以在清单与行程日期之间移动，支持拖动和批量移动／删除。参考[产品介绍](https://wanderlog.com/plan-a-trip)、[移动地点](https://help.wanderlog.com/hc/en-us/articles/5159751100443-Move-a-place)、[批量操作](https://help.wanderlog.com/hc/en-us/articles/5159691054619-Move-or-delete-multiple-places-at-once)。可借鉴先收集、后分天，以及一次整理一组地点；不照搬其预算、订单与协作复杂度。
3. Google Maps 地点清单：搜索地点后保存进清单，可以随后补充评论，清单支持编辑／删除，修改自动保存。参考[地点清单帮助](https://support.google.com/maps/answer/7280933?co=GENIE.Platform%3DDesktop&hl=en)。可借鉴低门槛收集和可逆编辑；只是交互参考，不建议在国内改用 Google 底图。

以下方向是基于案例和本项目场景作出的建议，不是来源产品均已提供的功能。

## 建议的操作逻辑

### 先收集，再安排，最后按需补细节

允许从一个目的地或一句旅程名称开始，名称可自动生成后修改；日期和总天数不应阻止开始。尚未决定放在哪天的地点，先留在同一旅程的“待安排”中，不必创建另一套收藏流程。

普通添加默认搜索，显示名称、地区／地址及地图预览以分辨同名地点。选中即可加入当前天或待安排，继续搜下一个，不反复退出搜索再打开表单。名称、地址、坐标和地区由搜索结果带入；详细时间、备注、用途在添加后按需展开。

地点搜不到时仍可保存名称，不猜测坐标。地图微调先从搜索结果或附近已知地点定位，再移动地图／标记确认；户外无名路口、入口位置偏移是这类补充操作的适用场景。经纬度与坐标系不放入日常创建／添加流程，必要时只留在独立的导入／专业路径工具中。

### 整理要支持连续和批量操作

- 多个搜索结果连续加入；后续可评估多选后统一加入。
- 地点直接调整顺序，支持批量移到某天。手机除拖动外保留明确的移动操作，避免长按与滚动冲突。
- 天数随安排增加，日期确定后统一映射；不是每一天都要求填写主题、地区与住宿。
- 移除一天时让人选择迁移其地点或一并移除，不要求手工逐条清空。
- 操作即时反馈；自动保存要明确区分正在保存、服务器已保存和失败待重试，不能把本机草稿说成已保存。普通移除优先支持撤销，整旅程删除保留明确确认。
- 可以粘贴一行一个地点名称并批量匹配；匹配后集中复核同名／模糊地点，未匹配的名称继续保留。该项为候选能力，不依赖 AI，也不承诺首轮全部实现。

### 规划与户外路径分层

旅游规划先解决“去哪些地方、先后顺序、哪天去”，地图辅助判断远近。交通是地点之间的关系，尽量在相邻地点间调整，允许整天设默认方式再改例外，避免每加一个地点都选一次。

可以建议顺路分组，但不擅自重排有预约、固定交通或个人偏好的安排。徒步路线则允许把一串地名确认后整体送入算路／导入流程，再集中处理异常路段，避免每段重复走专业表单。候选路径仍需注明来源，地点顺序不等于真实走过的轨迹。

### 补记与删除不能留到最后

已有计划的回程补记，应复用计划候选地点，让人批量勾选实际去过的地方、移除没去的、加临时地点；不能静默把全部计划转成已到访。没有计划的旅程也可直接补记，照片可选，不要求写日记。

明确提供旅程删除。空白／误建旅程删除应轻量；已有照片、到访或分享的旅程需说明影响。具体关联资料保留／取消关联、撤销或回收方式必须在实施前明确，不把删除旅程直接等同于删除独立相册原图。归档是保留记录，与删除分开。

## 后续用来检验方案的真实任务

不是按按钮数量验收，而是检查是否能少中断地完成任务：

1. 日期未定，先收集武汉几个想去的地点，不被迫先分天。
2. 两天游，连续加入黄鹤楼、湖北省博物馆、东湖等地点，再按距离安排；同名 POI 能辨认。
3. 七天游，批量移动一天的地点，改变日期与次序，不逐个打开详细表单。
4. 虎跳峡已有一串客栈／路口名字，确认地点后形成连续规划，无名点才手动微调。
5. 回来后只确认真正到访的地点、补少量照片，不复制填写整份计划。
6. 新建错了可删除；移错、删错地点可撤销；网络失败能知道哪些还没保存。

先讨论并验证以上任务的操作路径，再确定页面结构、原型提示词和实施拆分。暂不选择最终视觉布局，也不将自动分天、文本批量导入或 AI 安排记为已确认需求。

### 发现与后续建议

1. **跨天批量移动打乱组间顺序，建议修正。** 先选择第 1 天的黄鹤楼，再选第 2 天的湖北省博物馆，统一移回待安排。既有江汉路后出现“湖北省博物馆 → 黄鹤楼”，与原天数顺序相反。源码 `movePoints` 对各组逆向遍历后统一 `unshift`，保留了组内顺序，却反转了组间顺序。建议按原行程天数及组内顺序收集后统一追加，并明确保留规则。
2. **成功反馈遮挡地图地点摘要，建议修正。** 393×775 下移动提示条高 68px、位于 y=623–691；地图摘要位于 y=637–710，实际重叠。提示默认停留九秒，连续操作会带到下一视图。建议缩小普通成功反馈、缩短停留并避让摘要，保留撤销入口的可达性。
3. **地图仍不足以判断细位置。** 主地图只有行政区轮廓、编号点及示意线，没有道路、地名和建筑参照；上海中山公园的微调画面几乎是纯底色加中心标记。这不是脚本加载失败，而是原型采用的示意图限制。当前可评审搜索／确认动作，不能据此判断是否顺路、入口是否精确。进一步视觉评审可使用有道路与地名的底图预览或标注足够参照，应用接入时沿用真实高德搜索与 2D 底图。
4. **已加入结果再次点击会取消。** 原型明确提示“已加入·点击取消”，避免重复写入，但与首版提示词的“已加入禁用”不同。当前视为待评审选择而非重复添加故障；需权衡快速反选与滑动／误触后移除的风险。

判断：轻量创建、连续地点搜索、待安排后分天的主结构已可作为后续讨论基线。优先处理顺序与反馈遮挡，再完善地图参照；无需继续堆叠功能。此结论不代表用户已批准应用迁移，也不代表生产删除规则或本地原型中的到访删除语义已定稿。
